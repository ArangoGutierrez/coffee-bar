The chosen power policy can interrupt other applications' work. The user explicitly
selected a Mac sleep request even when other apps hold wake assertions. The user
also selected immediate release on missing power data rather than a grace period.
The socket-lock review raised a valid legacy-liveness concern: the implementation
therefore refuses ambiguous recovery. A stopped legacy node or missing ownership
metadata can require manual recovery.

The user selected preservation when the lid journal's directory or transaction
lock is unsafe. The helper reports the fault and requires path repair before
further lid changes. It does not restore a global power setting without a safe
transaction lock. A secure but non-private `0755` journal directory still allows
the existing refusal recovery under the lock; an unsafe `0777` directory does
not. This can leave a prior lid setting active until repair. The app releases
its own wake assertion and reports the helper failure.

Arming now rejects an unreadable or empty boot identity before journal,
watchdog, or power changes. A separate watchdog process can still fail its own
identity read. The current helper interface has no health acknowledgement.
The transaction lock makes an overlapping watchdog evaluation return busy;
the production loop retries after five seconds. The user selected this retry
contract after review raised the lack of a health acknowledgement. Arming
success confirms that the journal is present; it does not prove that the
separate watchdog is healthy. The regression checks the busy result,
then verifies that a later failed identity check restores the recorded power
value, clears the journal, and stops the watchdog.

## Test quality and remaining limits

New regressions exercise actual pipe and socket behavior, not only source text.
Fake power, helper, and clock seams keep the suite from sleeping this Mac.
Non-timeout helper tests control deadline completion so suite scheduling cannot
substitute the timeout path for the intended completion path. The production
timeout and a separate real-timeout regression remain unchanged. Continuation
preconditions fail the test before an empty queue can crash the test process.
An existing clock test failed because independently converted `Double` seconds
differed by one ULP. A 20,000-sample control reproduced a maximum one-ULP
difference. The test now allows two rounding steps. The clock-rate and
continuous-clock checks remain in place; production clock code is unchanged.
The arm-contention test now requires its worker handshake, records the first
arm's result, uses a fixed boot identity, and releases the worker on failure.
The earlier failure did not establish whether scheduling or an early error
prevented entry. The overlap and recovery assertions remain in place.

A later full run timed out while the child-process lock test waited for its
readiness callback. A controlled shared-pool exhaustion check showed that the
child's readiness byte could be available while that callback could not run.
The failing full-run log did not establish the child's timing. The harness now
uses a bounded direct poll and requires the exact readiness byte; EOF and a
wrong byte are rejected. A child-owned alarm and bounded parent wait control
cleanup without a PID signal. The pool-exhaustion check remains diagnostic
evidence outside the normal suite. Lock contention, unchanged power and journal,
and successful recovery after child exit remain asserted.

Remaining risks and follow-up work:

- Session stale expiry still uses wall time. A backward clock step can extend a
  stale working session. The independent battery floor limits battery risk.
- Terminal history is capped; active unique session IDs are not count-capped.
  Same-user event floods can still increase memory and per-event work.
- Assertion-release failures are not fully observed. No retained system
  assertion was reproduced in this audit.
- The large `ServingModel` remains a maintenance concern. Broad extraction and
  removal of public APIs are outside this fix.
- Structural source-text tests are brittle. They complement behavior tests but
  do not prove runtime safety.
- Hardware acceptance with lid closed, a real helper, another app's wake
  assertion, and sleep/wake remains required before release. No code can promise
  that macOS will accept or complete every sleep request.
