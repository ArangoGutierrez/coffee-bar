# v0.2.1 — upgrading delivers the fix

**Date:** 2026-08-09
**Status:** approved, not yet implemented
**Base:** `main` @ `82a4cc2`, immediately after the v0.2.0 cut

## Why this release exists

v0.2.0 is the first release that installs a **root** binary. It is therefore the
release that created a new class of defect: a privileged component whose lifetime
is longer than the app that placed it.

v0.2.1 is the first release that must **update** one. Everything here follows
from that sentence, and it is the reason this is a patch rather than a batch of
unrelated fixes.

Two of the three items were discovered by cutting v0.2.0. That is the argument
for cutting releases deliberately rather than tagging and hoping.

## Scope

Three defects. No new surface, no new UI, no new network behaviour.

### 1. The stale privileged helper

**Measured on a real upgrade, 2026-08-09.** After installing v0.2.0 over
v0.2.0-rc3, `/Library/PrivilegedHelperTools/coffee-bar-probe` was still the rc3
binary, dated `Aug 8 22:22`. Installing an app does not touch it, and nothing in
the product compares the two.

The consequence is not cosmetic. The whole point of rc3's privileged-path work —
the `uninstall` ordering fix, the `mach_continuous_time()` TTL fix, the
notification sequencing fix — is that a root component behaves safely. A user who
armed under an older build keeps executing the older root binary indefinitely,
and no future fix to that path can reach them.

**Design: detect and tell.** The app hashes its bundled probe and compares it
against the installed one, which is `-rwxr-xr-x root:wheel` and therefore
world-readable — no privilege is needed to read it. When the bytes differ, raise
the advisory that already exists for a missing helper, carrying the
`sudo install -o root -g wheel -m 755 …` command `ServingModel.swift:427` already
builds.

**What this deliberately does not do**, and why:

- **The probe does not update itself when armed.** It runs as root, and the
  bundle it would copy from lives in `/Applications`, which macOS ships
  group-writable. A root process installing a binary from a group-writable
  directory is the escalation `PathSecurity` and issue #75 exist to prevent. The
  convenience is not worth re-opening that door.
- **The app does not elevate.** `ServingModel.swift:400` states the rule the
  product is built on: *"it never elevates its own privilege, so the user runs
  the copy in their own shell."* Comparing two files needs no privilege;
  installing one does, and that stays with the user.
- **`SMAppService` (#71) is not adopted here.** It is the correct long-term
  answer and removes this defect class rather than reporting it, but it is a
  redesign of the privileged path. Adopting it would delay the very fix that
  makes future privileged fixes deliverable.

### 2. The app inside the disk image is not stapled

**Measured, both images mounted 2026-08-09:**

| Release | `xcrun stapler validate` on `CoffeeBar.app` inside the image |
|---|---|
| v0.1.1 | `The validate action worked!` |
| v0.2.0 | `CoffeeBar.app does not have a ticket stapled to it` |

A regression. `scripts/release-dmg.sh` notarises and staples the **image**; the
app a user drags out of it carries no ticket of its own. Stapling exists so
Gatekeeper can verify without a network round-trip, so a first launch on an
offline machine has nothing local to verify against.

**Design.** Notarise the app before assembling the image, which is a separate
submission from the image's:

```
sign app  → ditto -c -k --keepParent → notarytool submit → staple APP
          → assemble DMG → sign DMG → notarytool submit → staple DMG
```

**This doubles the Apple round-trips per release**, from one to two. That cost is
stated here rather than discovered during the next cut. It is what v0.1.1 did,
and it is why v0.1.1's app carried a ticket.

**Not verified:** the offline failure mode itself. The claim that an unstapled
app fails a first launch without network is Apple's documented reason for
stapling, not something measured on this machine. The v0.2.1 acceptance should
include an actual offline launch, because a diagnosis is a hypothesis until it
is executed.

### 3. `HookHealth` reports `.wired` for a hook that cannot fire (#55)

`HookHealth.swift:252` iterates the matcher groups and reads the inner `hooks`
array, matching on the command string. The loop variable is named `matcher` while
the key of that name is never read, so a tool-event group with **no** `matcher`
passes exactly as a correct one does.

`docs/QUICKSTART.md:128` states the contract this must enforce:

> The two tool events take `"matcher": "*"`; the other three take no matcher.

This is not hypothetical: `~/.codex/hooks.json` was merged without matchers on
2026-08-06, and for a full day the panel reported Codex as wired while no Codex
tool event could reach the ingest socket. A health check that answers `.wired`
when the answer is no converts a fixable misconfiguration into an invisible one.

It belongs in this release because it is the same failure as items 1 and 2: the
product telling the user something is fine when it is not.

### 4. Two architectural justifications rest on a premise that is now false (#86)

Added 2026-08-10, after the other three, during a backlog audit.

`Sources/CoffeeBarProbe/main.swift:13-14` and
`Sources/CoffeeBarPower/LaunchDaemonInstaller.swift:14-15` both state that the
only bundle that ships is Homebrew-built and ad-hoc signed, with
`TeamIdentifier=not set` and `codesign -R='anchor apple generic'` exiting 1.

Measured against the shipped v0.2.0 app by running the exact command the
comments cite:

```
codesign -v -R='anchor apple generic' /Applications/CoffeeBar.app   → rc=0
TeamIdentifier=85FN4Z37V8
Authority=Developer ID Application: … (85FN4Z37V8)
```

All three claims are false. They are load-bearing: they are the recorded reason
for not pinning an XPC peer, which `SECURITY.md` requires, and for not adopting
`SMAppService` (#71). A reader is told a check is impossible when it is now
merely unimplemented.

**Comment-only.** No behaviour changes, and the architecture is NOT re-derived
here — whether to act on the unblocking is #71's question, and #71 now carries
the measurement.

It belongs in this release for the same reason as the other three: the tree
states something untrue and nothing notices.

## Out of scope, with reasons

- **#29 check for updates.** Thematically ideal for a release about upgrading,
  and excluded anyway: it requires network egress, and `docs/ROADMAP.md:88`
  commits SECURITY.md to *"makes no network egress"*. Changing that is a
  security-claim decision with its own design, not a patch item.
- **#71 `SMAppService`.** See item 1.
- **The v0.2.2 milestone.** 18 open issues, never started. #51 (tool selection)
  and #52 (the first-run wizard) are the release that makes the app pleasant;
  this is the release that makes it honest.

## Acceptance

1. Installing a build whose probe differs from the installed helper raises the
   advisory, and the advisory carries a command that works when pasted.
2. `xcrun stapler validate` passes on the app **inside** the built image.
3. A first launch of the copied app on a machine with networking disabled
   succeeds. Measured, not assumed.
4. A tool-event hook group with no `matcher` is reported as not wired, and one
   with `"matcher": "*"` is reported as wired. Both directions asserted.
5. Full suite green from a cold scratch path, with the three known
   load-sensitive flakes judged by isolated `--filter` runs.
6. `CHANGELOG.md` and `site/changelog.html` gain the entry together, with the
   eight release facts measured from the shipped artifact.
