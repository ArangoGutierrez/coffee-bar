# v0.1 acceptance — run by hand, on real hardware

This is the run that decides whether v0.1 is true. Every step below is something
the 431-test suite **cannot** establish: that a live Claude Code session drives
the power assertion with nobody touching a toggle.

Steps 0-6, 8 and 9 take about fifteen minutes. **Step 7 adds up to 25 minutes,
almost all of it waiting** — see that step. Run it all before cutting the tag.

> **First executed 2026-07-30.** Four steps did not match reality and are
> corrected below. The original warning stands for every future change: if a step
> does not match reality, the step is the thing to fix.
>
> **Second execution 2026-07-31, against `ff30eef`. Steps 3, 4, 5, 6, 8 and 9
> PASS. Step 7 was not run.** This was the first time the product was operated
> at all. Four more steps did not match reality; all four are corrected below.
> The run record is at the end of this file.

## 0. Quit anything already running

An earlier build left a stale bundle running once tonight and cost two
exchanges of confusion. Two instances also fight over the ingest socket.

```
pgrep -x coffee-bar
```

**Use `-x`, not `-fl`.** `pgrep -f` matches the whole command line, so any shell
sitting in a directory called `coffee-bar` matches. On the first real run
`pgrep -fl coffee-bar` returned three hits, all of them editor and agent shells
holding the repo PATH, with no instance running at all.

Quit anything listed from its own menu, or `kill` it by pid. Then confirm BOTH:

```
pgrep -x coffee-bar
pmset -g assertions | grep -i coffee-bar
```

Expect no output from either. **The first one is not optional.** Both bundles
share a `CFBundleIdentifier`, so if an instance survives, `open` on a different
bundle path does NOT launch that binary — LaunchServices just activates the
running one. The app comes to the front and you conclude it relaunched. This cost
three attempts on the first run.

## 1. Build the bundle

**Decide which commit you are certifying, and prove it.** The line below builds
whatever branch this checkout happens to be on. On the first run that was `main`,
28 commits behind the release candidate, so the whole run certified code that was
not being shipped.

```
cd <the tree you intend to release>
git log --oneline -1          # paste this into your run record
scripts/build-app.sh
```

`build-app.sh` resolves its own root from `BASH_SOURCE`, so running it from a
git worktree correctly builds THAT worktree. Use a worktree when the release
candidate is not the branch in your primary checkout.

Expect the glyph count, `LSUIElement=true (no Dock icon)`, and a built path. The
script REFUSES if a foreign `.app` sits in `build/`, and WARNS if an instance is
already running.

**Then prove the bundle is the code you just built**, before you trust anything
downstream:

```
ls -l build/CoffeeBar.app/Contents/MacOS/coffee-bar   # mtime NEWER than the commit
```

## 2. Install the hooks

coffee-bar **never writes your settings file**, and no verb prints this block, so
paste it yourself. Add to `~/.claude/settings.json` under `"hooks"`:

> **Corrected 2026-07-31.** This step used to say coffee-bar "has no CLI".
> `CoffeeBarProbe/main.swift` has a verb dispatcher with a usage block and the
> verbs `run`, `arm`, `report`, `revert` and `watchdog`. What is missing is a
> hooks verb, not a CLI. Design §6's "re-offer the snippet" is therefore a small
> addition to a tested dispatcher, not new ground.

```json
"SessionStart":     [{ "hooks": [{ "type": "command", "command": "curl -sS --fail-with-body --max-time 5 --unix-socket \"$HOME/Library/Application Support/coffee-bar/ingest.sock\" -X POST --data-binary @- http://localhost/event" }] }],
"PreToolUse":       [{ "matcher": "*", "hooks": [{ "type": "command", "command": "curl -sS --fail-with-body --max-time 5 --unix-socket \"$HOME/Library/Application Support/coffee-bar/ingest.sock\" -X POST --data-binary @- http://localhost/event" }] }],
"PostToolUse":      [{ "matcher": "*", "hooks": [{ "type": "command", "command": "curl -sS --fail-with-body --max-time 5 --unix-socket \"$HOME/Library/Application Support/coffee-bar/ingest.sock\" -X POST --data-binary @- http://localhost/event" }] }],
"PermissionDenied": [{ "hooks": [{ "type": "command", "command": "curl -sS --fail-with-body --max-time 5 --unix-socket \"$HOME/Library/Application Support/coffee-bar/ingest.sock\" -X POST --data-binary @- http://localhost/event" }] }],
"Stop":             [{ "hooks": [{ "type": "command", "command": "curl -sS --fail-with-body --max-time 5 --unix-socket \"$HOME/Library/Application Support/coffee-bar/ingest.sock\" -X POST --data-binary @- http://localhost/event" }] }]
```

Those five are exactly `HookHealth.requiredEvents`. Fewer, and the panel says so.

**`--fail-with-body` is not decoration.** Without it curl exits 0 on an HTTP
error, so a refused event disappears with no message anywhere and the session
stays `.working` forever — which means the hold never releases. That was
measured: a `Stop` post the listener answered with 413 gave exit 0 and an empty
stderr. With the flag the same post gives exit 22 and prints
`curl: (22) The requested URL returned error: 413`. A post the listener accepts
still exits 0, so only a real refusal is ever reported.

**`--max-time 5` is not decoration either.** Without it a listener that binds but
wedges leaves `curl` waiting for ever, and because this is a `PreToolUse` hook,
EVERY tool call in EVERY Claude Code session on the machine stalls behind it.
That failure is not hypothetical: M2 task 8b measured a nested-run-loop wedge
where the socket appeared, `curl` connected into the backlog, and the run hung
until it was killed at ten minutes. A hook is the worst place to omit a timeout,
because the blast radius is the user's whole tool chain and not just this app.
Five seconds is far above any healthy post, which completes in milliseconds.

**Two things to watch.** Hook config may only load at session start, so a session
already running will not pick these up. And the health check reads **only**
`~/.claude/settings.json` — hooks in a project's `.claude/settings.json` work but
are invisible to it, which is why the panel's wording no longer claims events are
absent.

> ### WARNING, added 2026-07-31 — read this before you measure anything
>
> **Once these hooks are installed, EVERY Claude Code session on the machine
> drives the assertion — including the session you are using to run this
> checklist.** That is correct behaviour and it is also the single biggest trap
> in this document. On the second execution it produced two false conclusions in
> a row: a hold at step 3 that looked like a bug, and a "never releases" at step
> 6 that was really three overlapping sessions each holding until its own idle.
>
> Rules that follow from it:
>
> - **Only one agent session may be active while you measure.** Count them in the
>   panel: it prints "N sessions working".
> - If an agent is helping you run this checklist, it must make **no tool calls**
>   while you read `pmset`. Its own tool calls create a session and take a hold.
> - A hold you did not expect is far more likely to be another session than a
>   defect. Identify the holder before you diagnose.
>
> **Unresolved.** On 2026-07-31 a session started 20 minutes AFTER the settings
> edit produced no events at all, while later sessions produced them reliably. The
> "may only load at session start" hedge above is therefore not the whole story
> and the real rule is unknown. Until it is known: after editing hooks, start a
> fresh session and confirm events arrive BEFORE trusting any negative result.

## 3. Launch, and confirm it is holding nothing

```
open build/CoffeeBar.app

```

```

Expect **no output**: `.auto` with no sessions holds nothing.

## 4. THE CLAIM — an agent session drives the assertion

Start a Claude Code session **in a different terminal**, in any repository, and

While it works:

```

**You touched no toggle.** That is the sentence the README makes and the reason

The panel should also show the session, per design §14 — a `.working` session

## 6. It lets go when the agent stops

Let the agent finish and wait for it to be idle at a prompt.

```
pmset -g assertions | grep -i coffee-bar
```

Expect **no output**, within about 30 seconds — the refresh interval.

`Stop` maps to `.awaitingInput`, and with `holdAwakeWhileBlocked` false the hold
drops. The machine sleeps while it waits for **you**, and wakes into work when
you answer. That is the whole product in one behaviour.

---

## 7. A crashed agent does not pin the machine forever

Start an agent working again, confirm the assertion, then **kill the process**
rather than letting it finish.

```
pmset -g assertions | grep -i coffee-bar
```

Expect the assertion to disappear once the stale timeout elapses. Nothing reports
a crash, so expiry is the ONLY thing that releases it — which is why staleness is
a safety property here and not a nicety.

> **How long, added 2026-07-31.** The doc used to say "once the stale timeout
> elapses" without a number, which is very likely why this step had never been
> run. The number is `StalePolicy.standard.workingTimeout` = **900 seconds, 15
> minutes**. It has a hard floor: Claude Code documents a 600 s maximum Bash
> timeout, and nothing fires between `PreToolUse` and `PostToolUse`, so any value
> at or below 600 would retire a HEALTHY session mid-build.
>
> **Measured expiry runs LATE.** Two synthetic sessions with no `Stop` released
> after **917 s** and **1270 s** against the 900 s timeout. The 41 % overshoot is
> consistent with App Nap throttling the 30 s refresh timer for an `LSUIElement`
> app — which "Known limits" predicted and this run confirms.
>
> **So allow 25 minutes before calling this a failure**, and check the panel for
> other working sessions first: any one of them holds the machine on its own.

## 8. Off means off

Set the control to **Off** while an agent is working.

```
pmset -g assertions | grep -i coffee-bar
```

Expect **no output**. `.stop` is an absolute veto that decides before the wake
predicate runs. A power tool that ignores "off" is a trust failure, which is why
`.stop` outranks the sessions.

Set it back to **Auto** and confirm the hold returns while the agent works.

---

## 9. Quit leaves nothing behind

Quit from the panel.

```
pmset -g assertions | grep -i coffee-bar
ls -l ~/Library/Application\ Support/coffee-bar/ingest.sock
```

Expect no assertion. The socket file **remains** — `stop()` deliberately does not
unlink it, because an orphaned model deleting a live instance's socket would kill
ingest silently. The next start connect-probes it and reclaims it.

## If a step fails

That is a good outcome discovered cheaply. Steps 4, 5 and 6 are the milestone;
7, 8 and 9 are the safety properties. Note which one, with the `pmset` output,
and it becomes the next task.

## Known limits of this run

- The panel cannot tell you the listener failed to bind. `startMonitoring` throws
  when a second instance owns the socket and `main.swift` only logs it. Task 8
  was asked to separate "hooks installed" from "listener running".
- `App Nap` throttles the 30s timer for a `LSUIElement` app, which makes step 7
  late rather than wrong. **MEASURED 2026-07-31**: expiry at 917 s and 1270 s
  against a 900 s timeout. No longer a hypothesis.

## What this run cost, and why

About four hours, of which roughly one was spent diagnosing a defect that did not
exist. The measuring agent's own tool calls were creating sessions and taking
holds while it tried to observe someone else's. Three overlapping sessions made a
correct release look like "never releases".

**The instrument was the bug.** That is now the warning at step 2 and the
precondition at step 3.

## Observations that are not defects, and not yet decisions

- Working sessions get a COUNT; blocked sessions get NAMES. Design §14 asks that a
  `.working` session be visible, and a count is the weak form of that. Whether to
  name them is a v0.1/v0.2 call, not a bug.
- A user who installs the hooks and has not launched the app gets
  `curl: (7) Failed to connect` on EVERY tool call in EVERY session. Exit 7 is
  non-blocking so nothing breaks, but it is noisy. "The app is not running" is a
  legitimate state, not an error, and it should probably be quiet — while a real
  refusal stays loud, which is what `--fail-with-body` is for.
